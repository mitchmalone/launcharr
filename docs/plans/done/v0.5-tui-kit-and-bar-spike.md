# v0.5 slice 1 — TUI component kit + bar window spike

## Goal

Two foundations for the 0.5 menubar-replacement direction: `packages/tui` (the
Omarchy-inspired TUI component library every 0.5 surface will be built from) and a
minimal always-visible bar window that answers the one open feasibility question —
resident memory of a webview bar.

## Context

Direction settled 2026-08-15 (DECISIONS): own bar, wrapped Aerospace, modular install,
not a distro. Design references: Mitch's Omarchy screenshots (2026-08-15) — charcoal
panels, thin light border, monospace two-column hotkey menus, drill-down menus with
icons, rich panels (audio mixer, wifi, usage bars, calendar with year/life progress),
two-pane clipboard search, bar with workspaces left / clock center / status glyphs right.

## Approach

- `packages/tui`: pure React + CSS (no runtime deps beyond react), theme via CSS
  custom properties compatible with the existing launcharr theme system. Keyboard
  navigation logic (roving focus, list nav, drill-down menu state) is pure TypeScript,
  TDD'd in Vitest. A Vite gallery app inside the package for eyeballing.
- Bar spike: `bar.rs` creates one status-level, non-activating, all-spaces window per
  display; React bar view renders workspaces (aerospace CLI when present), clock,
  battery. Off by default (`bar.enabled` in config.json); Mitch's daily launcher is
  untouched unless enabled. Measure RSS with the bar up.

## Out of scope

Aerospace vendoring/installer, module API, wifi/calendar/bluetooth modules, notch
work, migration from user Sketchybar, invariant renegotiation.

## Risks / open questions

- R: WKWebView per display blows the memory budget → fallback discussion (shared
  webview tricks, native bar strip) happens with data, not vibes.
- R: `topmost`/level interplay between bar windows and the summon panel.
- Q: does the bar share the panel's webview process pool? (Measure, then read.)

## Measurements (2026-08-15, MacBook built-in display only, release build)

Fresh-launch RSS summed across launcharr + its WebKit helper processes:

| Configuration    | Main process | Helpers                             | Total   |
| ---------------- | ------------ | ----------------------------------- | ------- |
| Bar off          | 103 MB       | GPU 25 + WebContent 46 + Net 13     | ~187 MB |
| Bar on (settled) | 96 MB        | GPU 22 + WC 42 + WC(bar) 35 + Net 9 | ~205 MB |

**Marginal cost of one bar ≈ 19 MB** — it shares the app's existing WebKit process pool
(one extra WebContent process, no new GPU/Networking). Main-process RSS, the number the
120 MB idle budget has historically tracked, is unchanged (~96 MB).

**Go/no-go: GO.** The feared per-bar 50–100 MB webview baseline does not materialize;
wrapping Sketchybar buys nothing on memory worth its seams. Follow-ups for B2: repeat
with an external display attached (needs the multi-monitor enumeration fix), and after
a multi-hour soak.
